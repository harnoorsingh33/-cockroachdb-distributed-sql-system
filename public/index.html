Fault Tolerance & High Availability Simulator

CockroachDB tolerates $(N - 1)/2$ node failures. In this 3-node cluster, when 1 node goes down, quorum ($\lfloor 3/2 \rfloor + 1 = 2$) is maintained, allowing uninterrupted reads and writes.

Phase 1

Cluster Normal

All 3 nodes are active. Writes replicate to all 3 nodes. Raft leader coordinates writes across quorum.

Phase 2

Simulate Node 1 Down

Execute in your host terminal:

docker compose stop roach1
Phase 3

Restore Node 1

docker compose start roach1

Distributed Database Architecture & Theory

1. Distributed SQL & Horizontal Scaling

Unlike traditional monolithic RDBMS (PostgreSQL, MySQL), CockroachDB scales horizontally by distributing tabular data across multiple physical nodes while providing standard ANSI SQL and full ACID guarantees.

2. Raft Consensus Algorithm

Every range forms a Raft consensus group. For each write, the Raft Leader broadcasts log entries to followers. A write is committed once a majority ($Q = \lfloor n/2 \rfloor + 1$) acknowledges, preventing split-brain.

3. Multi-Raft Architecture

Rather than a single bottleneck Raft log, CockroachDB runs thousands of independent Raft groups simultaneously—one per range. Each node can be leader for some ranges and follower for others.

4. Range Leases & Linearizable Reads

Each range elects a Leaseholder (usually the Raft leader). Reads are served directly by the leaseholder without consensus network hops, guaranteeing serializable consistency at high throughput.

5. CAP Theorem & Consistency

CockroachDB is a CP (Consistency & Partition-tolerance) system in Eric Brewer's CAP theorem. During network partitions, it preserves serializable consistency; surviving partitions with quorum continue serving traffic.

6. Fault Tolerance & Quorum

A cluster with $2f + 1$ nodes tolerates $f$ node failures. For our 3-node cluster ($n=3, f=1$), 1 node failure is fully tolerated without data loss or service disruption.
